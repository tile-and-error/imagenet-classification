2. Think of a pipeline as objects

A pipeline is a few objects, each with one job. Data flows one way through them.

flowchart LR
    D["DataLoader<br/>(torch)"] -- "batch dict" --> G
    subgraph G["ExecutionGraph (lwfm)"]
        direction LR
        N1["ModelNode 'student'<br/>holds an nn.Module"]
        N2["ModelNode 'teacher'<br/>(later)"]
    end
    G -- "{'student.logits': ...}" --> LC["LossComposer (lwfm)<br/>LossBindings"]
    G -- "same outputs" --> MB["MetricBindings (lwfm)"]
    LC -- "total loss" --> OPT["backward() + optimizer<br/>(torch)"]
    LC -. "events" .-> R["OutputRouter (lwfm)"]
    MB -. "events" .-> R
    R -.-> S["Sinks: files, console (lwfm)"]
ObjectIts one job
DataLoaderHands out batches (a plain dict).
ModelNodeWraps one nn.Module: says which values it reads and what it writes.
ExecutionGraphRuns the nodes in the right order. Returns every output by name.
LossBinding / LossComposerPick values by name, compute losses, add them up.
MetricBindingPick values by name, update a metric.
OutputRouter + sinksRecord what happened. Nothing reads back from them.

Two rules for drawing a pipeline

  1. A straight chain is plain PyTorch. Preprocessing → backbone → head is one nn.Sequential, inside one node.
  2. The graph is only for branches and merges. A teacher and a student reading the same image; a loss reading two models' outputs.
Why? PyTorch already handles chains well. We only build what PyTorch doesn't have: a clear way to say which model's output goes to which loss when several models run at once.
