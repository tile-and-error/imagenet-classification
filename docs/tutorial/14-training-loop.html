14. Inside fit: steps, epochs, validation

fit repeats one step per batch. Around the steps it counts, schedules the learning rate, validates, logs, and decides when to stop.

flowchart TD
    A(["fit(...)"]) --> C["checks before any batch<br/>(slide 18)"]
    C --> E["start an epoch: graph.train()"]
    E --> B["next batch: to_device"]
    B --> S["one step: forward, loss, backward, optimizer step"]
    S --> K["global_step += 1<br/>scheduler, if per step · log every N steps"]
    K --> M{"more batches?"}
    M -- yes --> B
    M -- no --> V["epoch += 1<br/>validate with the Evaluator (slide 7)"]
    V --> X{"stop?<br/>max_epochs · max_steps · a callback"}
    X -- no --> E
    X -- yes --> R(["TrainingResult"])
TermMeans
step (global_step)one optimizer update. max_steps and log_every_n_steps count these.
epochone full pass over train_loader. It only counts once the loader is used up.
validationafter every epoch by default, or every val_every_n_steps. Every run ends on a validation result.

Validation, logging and a learning-rate schedule

metrics = [MetricBinding("top1", MulticlassAccuracy(K, average="micro"), CE_READS)]  # lwfm + torchmetrics
epochs = 3
scheduler = torch.optim.lr_scheduler.CosineAnnealingLR(      # torch: lr falls to 0 ...
    optimizer, T_max=epochs * len(train_loader)              # ... over every optimizer step of the run
)
trainer = Trainer(device="cpu", max_epochs=epochs, log_every_n_steps=20)
result = trainer.fit(
    graph, train_loader, loss, optimizer,
    val_loader=val_loader, metrics=metrics,                  # lwfm: validate after every epoch
    scheduler=scheduler, scheduler_interval="step",          # lwfm: required with a scheduler
    output_sink=ConsoleSink(),                               # lwfm: print every event (slide 9)
)
result.best("top1")                                          # lwfm: the best validation, and its step

From PyTorch

  • CosineAnnealingLR — any torch.optim.lr_scheduler works; the trainer only calls scheduler.step().
  • MulticlassAccuracy — any torchmetrics metric, bound to names as on slide 6.

From lwfm (ours)

  • val_loader + metrics — always passed together; validation goes through the same Evaluator as slide 7.
  • curves=[CurveBinding(...)] — optional: a ROC curve, confusion matrix or other table, built from the whole validation set at every validation and written as eval/val/<name> (slide 7).
  • scheduler_interval — "step" (after each optimizer step) or "epoch". ReduceLROnPlateau needs a metric, so it is stepped from a callback's on_validation_end.
  • output_sink — receives trainer/settings once, then train/loss/*, train/lr, train/epoch_seconds and eval/val/*. With no sink, nothing is written.
Why must scheduler_interval be given? A schedule stepped per batch and the same schedule stepped per epoch differ by a factor of the epoch length. A default would silently change results when code is copied from elsewhere, so you always say which one you mean.
