11. Design decisions

DecisionWhy
Everything you train or run is a plain nn.Module.Works with all PyTorch tools, and with TIAToolbox later, without unwrapping.
ModelNode wraps models; it never subclasses them.Any model drops in unchanged: torchvision, timm, your own.
Straight chains use nn.Sequential; the graph is only for branches.PyTorch already does chains well. We only build what's missing.
Values are found by name: inputs.image, student.logits.The wiring is visible in one place, can go in a config file, and typos fail with the bad name.
Values go into models and losses by position.No need to know a model's argument names. Losses and metrics already take (prediction, target) in order.
A node only writes under its own name.Two nodes can't clash, and the node name is typed once.
Building the graph checks its wiring, then runs it once on a tiny batch to check shapes.Mistakes fail in a second, not after an hour of training, and the error names the node.
Preprocessing is part of the model.The shipped model can't forget it or apply it twice.
deployable_model returns one nn.Module, and you must name the node.We measure and ship the student alone; the graph doesn't guess which node that is.
A node runs once per graph(batch); readers share its output.Two heads on one backbone cost one backbone pass.
The Evaluator computes each metric once over all batches, and restores the graph's mode.Results don't depend on batch size, and validation during training leaves training mode on.
Results go through sinks; nothing reads back from them.Logging can't change training, and new destinations need no training-code changes.
Interfaces are abstract base classes with no shared code.Missing methods fail at creation; changing an interface can't silently change existing implementations.
A batch is a plain dict.DataLoader, saving and device moves already support it.
