5. ExecutionGraph: connecting models

An ExecutionGraph holds nodes and runs them in an order where each node runs after the nodes it reads from.

from lwfm.core.graph import ExecutionGraph               # lwfm

probe = ModelNode("probe", nn.Linear(10, 2),             # torch: a single linear layer
                  reads="student.logits", writes="logits")

graph = ExecutionGraph([probe, student])   # lwfm: the list order doesn't matter
graph.order                                # ['student', 'probe']
graph(batch)                               # one dict with every node's outputs
{'student.logits': [8, 10], 'probe.logits': [8, 2]}

A node runs once per call, however many nodes read it. Outputs go into one dict; every reader gets the same tensor from it.

shared = ExecutionGraph([
    ModelNode("head_a", nn.Linear(16, 2), reads="backbone.features", writes="logits"),
    ModelNode("head_b", nn.Linear(16, 3), reads="backbone.features", writes="logits"),
    ModelNode("backbone", backbone, reads="inputs.image", writes="features"),
], sample=batch)    # backbone has no InputAdapter, so give a real batch for the shape check
shared.order       # ['backbone', 'head_a', 'head_b']: backbone runs once, both heads reuse it

Nothing is kept between calls: the next graph(batch) runs everything again on the new batch. Putting the same module object into two nodes runs it twice; that shares weights, not outputs.

Mistakes fail when the graph is built, before any data is used:

ExecutionGraph([ModelNode("probe", nn.Linear(10, 2), reads="studnet.logits", writes="logits")])
GraphError: 'probe' reads 'studnet.logits', which no node writes

Wrong shapes only show up when data flows, so building the graph also runs it once on a tiny batch (the preflight check):

graph = ExecutionGraph([student])          # sample="default": zeros shaped by the InputSpec
graph.shapes                               # {'student.logits': (2, 10)}, for the log
ExecutionGraph([student], sample=batch)    # or check with a real batch
ExecutionGraph([student], sample=None)     # or skip the check

probe = ModelNode("probe", nn.Linear(512, 2), reads="student.logits", writes="logits")
ExecutionGraph([student, probe])           # 512 should be 10: fails while building
RuntimeError: mat1 and mat2 shapes cannot be multiplied (2x10 and 512x2)
in node 'probe', reading student.logits (2, 10)

The check also fails if an output loses the batch size as its first dimension. It runs in eval mode with no gradients and leaves the graph in train mode; graph.preflight(batch) re-runs it later. The error keeps PyTorch's type. The note naming the node is added in ordinary runs too, and losses and metrics add one naming themselves.

From PyTorch

  • nn.ModuleDict — a dict of modules that PyTorch can see. The graph stores its nodes in one.
  • .parameters() .to() .train() .eval() .state_dict() — all work on the graph, because it is an nn.Module. Weights are saved under keys like nodes.student.module.1.fc.weight.

From lwfm (ours)

  • ExecutionGraph(nodes, sample="default") — checks names, finds the run order, checks shapes on a sample (graph.shapes), then graph(batch) returns {name: tensor}.
  • GraphError — raised for a duplicate node name, a read nothing writes, a loop, or an output that loses the batch dimension.
Why? With one node you barely need a graph, but distillation needs several models reading one batch. Building the general version now means adding a teacher later is one more list entry, not a second code path.
