10. Where to extend

Each kind of change has one place to go. If you find yourself editing the graph or a loop to add a technique, stop: there is a better place.

Example: a new sink and a new loss

from lwfm.results.sinks import OutputSink        # lwfm interface (an abstract base class)

class ListSink(OutputSink):                      # must define both methods,
    def __init__(self):                          # or Python refuses to create it
        self.events = []

    def write(self, event):
        self.events.append(event)

    def close(self):
        pass

def logit_penalty(logits):                       # a plain function is a valid loss
    return logits.pow(2).mean()                  # torch: returns one number

loss_fn = LossComposer([
    LossBinding("ce", nn.CrossEntropyLoss(), ["student.logits", "targets.class"]),
    LossBinding("penalty", logit_penalty, "student.logits", weight=1e-3),
])

From PyTorch

  • nn.Module — the extension point for anything that computes: models, adapters, projectors, learnable losses.

From lwfm (ours)

  • OutputSink — lwfm interfaces, written as abstract base classes (Python's abc.ABC). A subclass missing a method can't be created: the error lists what's missing.
  • DataModule, Stage, Benchmark — planned interfaces, same style.
Why? Each technique acts at one point (data, model, forward pass, loss, a whole step), so each gets its own small interface instead of one giant one. That way a technique is added without touching the trainer, and the baseline keeps working.
